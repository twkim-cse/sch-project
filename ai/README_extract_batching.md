# extract 후보 우선순위 및 무누락 배치 처리

## API 및 작은 요청

POST /ai/extract 요청과 성공 응답 JSON은 기존과 동일합니다. 입력이 25개 이하이고
입력 예산 안에 있으면 기존 순서 그대로 한 번의 생성 호출로 처리합니다.
특히 일반적인 6~10개 소규모 요청은 단일 호출입니다. 긴 원문은 조항 수가 적어도
길이 예산에 따라 여러 배치로 나뉠 수 있습니다.

## 후보 점수

### 6번 해약환급금의 직접 관련성

추출 지침에서 계산·산출 기준, 해지 시 반환 금액, 지급 조건·시기, 공제·차감,
해약환급금 청구권 행사기간·소멸시효, 금액·지급에 직접 영향을 주는 내용을 포함합니다.
일반 해지권·효력상실·대출 안내는 단어만으로 포함하지 않으며, 다른 항과 연결되면
환급 효과를 직접 설명하는 지급·차감 항을 중심으로 선택합니다. 관련 결과 개수를
강제하지 않습니다. 코드가 결과의 6번 번호를 자동 보정하거나 단어로 강제 제외하지 않습니다.

test_data/extract_refund_cases.json은 실제 약관이 아닌 가상 정답 사례입니다.
모의 테스트는 지침 전달, 요청 범위, 정답 형태의 결과 처리와 기존 기능 회귀를 검증합니다.
음성 사례의 빈 응답도 모의 설정이므로 실제 모델의 과다 분류 차단을 입증하지 않습니다.

### 1번과 2번의 추출 분류

생성 지침은 1번을 보험금 미지급 사유·적용 제외 조건, 2번을 기간부 보장 제한·감액 및
특정 질병/신체부위의 부담보 기간으로 구분합니다. 단순히 '면책'이라는 단어만으로
1번에 한정하지 않고 2번의 기간 근거를 별도로 확인하도록 합니다.
기간 없는 영구 제외는 억지로 2번에 넣지 않으며, 청구/지급기한·갱신주기를 면책기간으로
혼동하지 않도록 명시했습니다. 두 유형이 각각 명확하면 동일 조항의 복수 항목 추출을
허용합니다. 중복 제거 키는 (check_item, clause_id, 정규화 quote)이므로 1번과 2번이
서로 제거되지 않습니다. 실제 분류는 AI에 맡기며 코드가 번호를 강제 보정하지 않습니다.

삼성화재 40개 결과의 부담보 기간 조항은 원문 인용에는 성공했지만 1번만 반환됐습니다.
당시 2번 원본 반환 수가 0이므로 검증기나 중복 제거가 2번을 없앤 것은 아닙니다.
대량 입력의 문맥·순서 영향은 가능성이지만 모델 내부 원인은 확정하지 않았습니다.
새 가상 정답 사례는 오프라인 흐름 검증용이며 실제 AI 분류 정확도 평가가 아닙니다.

extract_planning.py의 score_clause가 요청한 check_items별 점수를 계산합니다.
면책·보상제외, 면책/감액/부담보 기간, 갱신·보험요율, 고지·통지, 의료 용어 정의,
해지/해약환급금 등 동의 표현을 사용합니다. 키워드 하나가 등장한 필드별로 제목 8,
section 3, 본문 1의 가중치를 더합니다. 반복 횟수로 점수를 계속 늘리지는 않습니다.
검색용 사본에서만 공백 제거·대소문자 정규화를 합니다. 원문 및 ID는 변경하지 않습니다.

후보 점수는 분석 순서만 결정합니다. 점수가 0이어도 후속 배치에 반드시 포함합니다.
상위 N개 제한이나 저득점 영구 제외는 없습니다. 점수는 확률이나 의미 정확도가 아닙니다.

## 그룹과 배치

같은 rider_id, section, article을 가진 조항은 원래 순서대로 그룹화합니다.
그룹 내 최고 항목 점수로 우선순위를 정하고 동점이면 최초 입력 순서를 사용합니다.
article 정보가 없으면 조항별 그룹으로 취급합니다.

그룹 전체가 배치에 들어가면 통째로 넣습니다. 그룹 자체가 너무 크면 원문을 자르지 않고
조항 경계에서만 나눕니다. 모든 ID의 기본 분석 배정이 정확히 한 번인지 검사합니다.
같은 조·같은 약관 범위에서 다음 배치 첫 조항이 다만/그러나/전항/제N항 등의
예외·참조 표현으로 시작하면, 예산 내에서 직전 항을 문맥용으로 추가할 수 있습니다.
사본은 same_article_boundary_exception_context 사유로 별도 표시하고 개수·고정 사유를
로그에 남깁니다. 사유 없는 중복, 누락 및 원문 변경은 계획 검증에서 거절합니다.
예산상 문맥 사본을 넣을 수 없으면 context_omitted_budget=true로 명시합니다.
의미적 관계의 완전한 판별이 아닌 제한적인 경계 문맥 보완입니다.
그룹을 나눠야 하는 경우 항·예외가 다른 배치에 갈 수 있고,
다른 조를 참조하는 내용의 완전한 문맥 해석은 보장하지 않습니다.
article/section/rider 메타데이터가 부정확하면 문맥 그룹도 부정확할 수 있습니다.

기본 상수:

- 배치당 최대 25개 조항
- 배치 입력 예산 24,000 UTF-8 바이트
- 입력 길이 = check_items 설명과 전체 조항 메타데이터를 포함한 JSON 바이트 수
  + 고정 시스템 지시 바이트 수 + SDK 포장용 여유 2,048바이트
- 요청당 최대 40배치

이는 실제 토크나이저 측정이나 모델의 공식 컨텍스트 한도가 아닌 보수적인 애플리케이션
예산입니다. 전체 요청을 호출 전에 계획합니다. 조항 하나라도 예산을 넘거나 40배치를
초과하면 Gemini 호출 전 HTTP 413 / EXTRACT_INPUT_BUDGET_EXCEEDED로 거절합니다.
백엔드는 조항 경계를 검토하거나 요청을 나누어야 하며 서버가 원문을 임의로 잘라내지 않습니다.

## 호출 및 검증

배치를 순차 처리하고 모든 배치의 raw 추출 결과를 합친 뒤 기존 validate_extractions로
요청 항목, 조항 ID, 공백 정규화 후 원문 부분 문자열, 자료형, 중복을 검사합니다.
인용의 글자·숫자를 고치지 않고 반환 quote도 유지합니다.

배치에서 API 또는 JSON/최상위 구조 오류가 발생하면 요청 전체가 기존 code/message
오류 응답으로 실패합니다. 앞선 배치의 일부 결과를 HTTP 200으로 반환하지 않습니다.
첫 배치 또는 중간 배치에서 429/503 재시도까지 최종 실패하면 즉시 중단하며
그 뒤의 배치는 호출하지 않습니다. 문맥 사본의 추출도 병합 후 최종 중복 제거합니다.
개별 잘못된 추출 행은 종전처럼 검증 단계에서 제외합니다.

response_mime_type=application/json을 유지하고 response_schema는 사용하지 않습니다.
각 배치의 429/503은 최초 1회 + 재시도 1회까지만 허용합니다. 429는 Retry-After,
RetryInfo, 기본 60초 순서이며 503은 2초입니다. 다른 오류는 재시도하지 않습니다.
extract와 explain은 기존 프로세스 공용 최근 60초 최대 10회 제한을 공유합니다.
실패한 시도와 재시도도 횟수에 포함됩니다. classify, 모델 목록 조회, 다른 프로세스는
포함되지 않으므로 계정 전체 RPM/RPD 준수를 보장하지는 않습니다.
일일 할당량 초과는 대기로 해결되지 않습니다.

## 호출 수와 처리 시간

짧은 가상 조항 Mock 기준:

| 조항 수 | 배치/정상 생성 호출 | 모든 배치가 1회 재시도하는 상한 |
|---|---:|---:|
| 6~10 | 1 | 2 |
| 100 | 4 | 8 |
| 300 | 12 | 24 |
| 500 | 20 | 40 |

실제 길이·그룹 구성에 따라 배치 수는 늘 수 있습니다. 요청 상한은 40배치/80시도입니다.
모델 목록 조회는 별도입니다. 순차 처리 시간은 배치별 지연의 합과 속도 제한·재시도
대기의 합입니다. 입력 토큰 전체를 크게 줄이는 검색이 아니므로 반복 지시/메타데이터
오버헤드와 호출 횟수는 늘어납니다. 각 호출의 기존 120초 제한은 요청 전체 제한이 아닙니다.
Spring/프록시의 요청 제한 시간과 일일 호출 예산을 실제 배포 전에 점검해야 합니다.

### 미검출 항목의 제한적 재확인(B안)

`extract_recheck.py`의 `ENABLED = False`가 기본값입니다. 활성화하려면 내부 상수를
True로 변경하고 서버를 재시작합니다. API 필드나 .env 설정은 추가하지 않습니다.
OFF에서는 기존 통합 추출과 호출 횟수를 유지합니다. 배포 시 이 모듈도 포함해야 합니다.

ON에서는 1차 원문 검증 후 결과가 없는 요청 항목만 살펴봅니다. 기존 점수가 양수이고
항목별 구체적 의미 단서도 있는 후보를 점수순으로 선택합니다. 점수와 단서는 정답이나
누락의 증거가 아닙니다. 같은 조의 조건·예외를 함께 포함하며, 그룹 전체가 예산에
들어오지 않으면 잘라 넣지 않고 생략합니다. 후보가 없으면 호출하지 않습니다.

재확인은 요청당 최대 3항목, 항목당 1개 번호만 전달하는 1회 확인입니다. 각 입력은
최대 12조항, 시스템 지침·JSON·통신 여유분을 포함한 UTF-8 16,000바이트입니다.
추가 결과가 빈 배열이어도 허용하며, 선택한 조항과 항목으로 원문 검증 후 병합합니다.
재확인 결과에 대한 재확인은 없습니다.

추가 생성은 최대 3회, 429·503의 호출당 1회 재시도를 포함해 실제 시도 최대 6회입니다.
기존 공유 호출 제한을 적용하고, 추가 단계 전체는 120초 예산을 사용합니다. 제한 대기와
재시도 대기도 예산에 포함하며 각 요청의 SDK 시간 제한은 남은 시간으로 설정합니다.
SDK 내부 자동 재시도는 이 추가 호출에서 비활성화합니다. 네트워크 취소·실행 환경에 따라
실제 반환 시각에 오차가 있을 수 있습니다. 전체 HTTP 처리시간은 1차 추출 시간까지 더해집니다.
일일 할당량 초과는 이 기능으로 해결되지 않습니다.

추가 호출의 최종 API/JSON/시간 오류는 기존 code/message의 HTTP 502로 종료합니다.
1차 성공 결과만 반환하지 않습니다. 제한 때문에 재확인하지 않은 항목은 관련 조항이
없다고 확정할 수 없습니다. 진단은 항목 번호·개수·입력 바이트·실제 추가 시도 수만 기록합니다.

### 4번 단독 요청의 고지·통지의무 지침

`app.py`의 `extract_instruction_for()`는 API 요청의 `check_items`가 정확히 `[4]`일 때만
고지·통지의무 상세 기준을 추가하고 JSON 예시 번호를 4로 맞춥니다. 의무 자체도 추출
대상이며 위반 불이익이 반드시 있어야 하는 것은 아닙니다. 일반 계약 의무는 제외하고,
원문 밖의 조건·불이익 생성은 금지하며 빈 결과도 허용합니다.
기존 공통 지침의 다른 번호 기준은 그대로 유지합니다. 변경된 시스템 지침 길이도
배치 입력 예산에 포함합니다. 혼합 요청의 기본 추출은 기존 공통 지침을 유지합니다.
B안은 실제 재확인 항목으로 지침을 선택하므로 혼합 요청에서도 3·4·5번 재확인에는 상세
지침을 적용합니다. `plan_rechecks()`도 같은 선택 함수를 받아 실제 지침 길이로 예산을
계산합니다. 1·2·6번 단일 항목은 공통 지침을 사용하며 6번 포함·제외 기준도 이에 포함됩니다.

`test_extract_duty.py`의 가상 데이터 회귀 9개를 포함한 전체 132개 오프라인 테스트 통과.
Mock은 실제 분류 정확도를 보증하지 않습니다. 실제 4번 단독 검증은 HTTP 요청/생성 각
1회, HTTP 200, 1,578ms, 원문 인용 1/1 통과였습니다. 이전 단독 기준의 0개 대비 1개
반환을 관찰했으나 단일 실행으로 일반적인 개선 효과나 원인을 확정하지 않습니다.

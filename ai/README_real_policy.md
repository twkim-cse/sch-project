보험 약관 AI 자동 테스트
======================

explain 호출 속도 제한 및 재시도 (2026-11-04)
-----------------------------------------

`/ai/explain`의 모든 generate_content 호출은 프로세스 공용 최근 60초 기록을
사용해 최대 10회로 제한합니다. 생성, 독립 검토, 재생성, 429/503 재시도와
실패한 호출을 모두 포함합니다. 제한에 도달할 때만 가장 오래된 기록이
만료될 때까지 기다립니다. 호출마다 고정 대기하는 방식은 아닙니다.

429는 Retry-After 헤더(초 또는 HTTP 날짜)를 우선 사용하고, 없으면 구조화된
google.rpc.RetryInfo.retryDelay, 둘 다 없으면 60초 대기 후 한 번 재시도합니다.
503은 기존대로 2초 후 한 번 재시도합니다. 오류 종류가 바뀌어도 같은 논리
호출은 최초 1회와 재시도 1회까지만 허용합니다. 재시도 전에도 속도 제한을
재확인하므로 실제 대기는 오류별 대기 시간보다 길 수 있습니다.
지속 실패 시 기존 HTTP 502를 반환하고 요청·응답 구조는 유지합니다.

일일 할당량 초과는 호출 간격 조절만으로 해결할 수 없습니다. 로그의
daily_quota_not_resolved_by_pacing은 이 제한을 알리는 고정 안내이며,
해당 오류가 일일 한도 초과로 확정되었다는 뜻은 아닙니다.
사용자가 제공한 RPM 15/RPD 500을 전제로 여유 있는 RPM 10을 목표로 하며,
실제 프로젝트의 할당량은 별도로 확인해야 합니다.

이 제한은 단일 프로세스의 explain 호출만 공유합니다. 여러 worker/서버,
다른 프로그램, classify/extract 호출은 이 기록에 포함되지 않으므로 전체
키의 할당량 준수나 429 방지를 보장하지 않습니다. 모델 목록 조회도 별도입니다.
프로세스를 재시작하면 호출 기록이 초기화됩니다.

여러 항목과 재시도가 겹치면 요청 처리가 길어집니다. 테스트 클라이언트의
--timeout 및 Spring/프록시 제한 시간을 고려하세요. 필요하면 항목을 나누어
순차 요청할 수 있으며 제한 기록은 요청 간에도 유지됩니다.

오프라인 회귀 및 속도 제한 검사:

```powershell
python -m unittest -v test_explain test_real_policy_mock
```

기존 서버와 .env를 변경하거나 가져오지 않는 별도 HTTP 테스트입니다.
실제 보험 약관 PDF는 제공되지 않았으며 실제 약관 테스트는 미실시입니다.
test_data/synthetic_policy.json의 모든 문장은 테스트용 가상 문장입니다.

실행
----

서버를 실행한 환경의 Python을 사용하세요. httpx가 필요합니다(google-genai의 의존성).

```powershell
# 입력 검사만 수행하며 서버 또는 Gemini를 호출하지 않습니다.
python test_real_policy.py

# 사용자가 명시적으로 실행: 서버를 거쳐 실제 Gemini 호출이 발생합니다.
python test_real_policy.py --run

# 특정 API만 실행
python test_real_policy.py --api extract --run

# 별도 입력 및 서버 주소
python test_real_policy.py --data test_data/real_policy.json --server http://127.0.0.1:8000 --run

# 네트워크 없이 모의 검증
python -m unittest -v test_real_policy_mock
```

--run이 없으면 HTTP 호출 및 결과 파일 생성이 없습니다. --run 실행 결과는
test_results/policy_test_날짜_시간.json에 저장됩니다. 실행 시각은 한국 시간입니다.
HTTP 클라이언트 제한 시간 기본값은 요청당 600초이며 --timeout으로 조절합니다.
여러 해설 항목은 항목당 2~4회의 Gemini 호출이 필요할 수 있습니다.
반환 코드: 0 성공(또는 입력 검사 성공), 1 API/검증 실패, 2 입력 오류.

검증과 결과
-----------

각 API의 HTTP 상태와 소요 시간, 응답 구조, 요청한 점검 번호, 원문 부분 문자열,
해설 item_id의 누락·중복, pass/fail 및 실패 이유 존재 여부를 검사합니다.
의미 검토 fail은 테스트 실패로 집계합니다. 모델명은 /health에서 가져옵니다.
모델명 확인 실패는 model_status=unavailable로 표시합니다.
빈 추출 결과는 구조적으로 유효합니다. 추출 재현율이나 의미 정확도에 대한
정답 라벨 평가를 자동 수행하지 않으므로 결과 수와 점검 항목은 사람이 확인하세요.

숫자 검사는 제목과 해설의 아라비아 숫자·단위를 원문과 문자 기준으로 대조하는
참고용 검사입니다. 쉼표와 공백만 정규화하며 숫자 자체는 출력하지 않습니다.
한글 수사, 단위 환산, 숫자의 문맥, 누락된 숫자, 같은 숫자의 다른 의미는 판별하지
못합니다. 경고는 실패로 집계하지 않습니다. 백엔드 최종 숫자 검증을 대체하지 않습니다.

결과/콘솔에는 원문, 해설, 인용, item_id, 서버 오류 본문, 예외 원문을 저장하지
않습니다. review_reason 내용 대신 존재 여부와 고정 실패 분류만 저장합니다.
API 키를 읽거나 출력하지 않습니다. 데이터 파일에는 원문이 들어가므로 비식별화하고
접근 권한을 관리하세요. --run 시 입력 원문이 서버 및 Gemini로 전송됩니다.

실제 약관 입력
--------------

실제 PDF는 별도 입력 데이터가 필요합니다. PDF 구조 분석 및 조항 분리는 Spring
백엔드 담당 영역이며, 이 도구는 PDF를 자동 분리하지 않습니다.
예제 JSON을 별도 파일로 복사하고 source_kind를 real_policy로 설정하세요.
requests 안의 필요한 API 데이터를 사람이 확인한 값으로 교체하세요.

- classify: document_id와 사람이 확인한 앞부분 pages(page, text)
- extract: analysis_id, check_items, 사람이 확인한 clauses
- explain: analysis_id, 사람이 확인한 items(원문 quote와 정확한 check_item)

요청은 서로 독립적인 고정 데이터입니다. extract 결과를 explain으로 자동 전달하지
않습니다. 실제 테스트 완료 표시는 --run으로 real_policy 데이터를 실행한 경우에만
나옵니다(실패 여부는 각 API 결과를 별도로 확인).

점검 번호: 1 면책 사유, 2 면책·감액기간, 3 갱신 보험료, 4 고지·통지의무,
5 질병·수술 등의 정의, 6 해지환급금.

현재 requirements.txt의 python-dotenvx 항목은 일반적인 python-dotenv 패키지명과
다릅니다. 이번 작업에서는 기존 파일 변경 금지에 따라 수정하지 않았습니다.

## 실패 / 재개

세 문서 × 전체/후보 × concurrency1/2/3/4의 24개 추가 시나리오에서 첫 요청을 503으로 실패시켰다.
실패를 관찰한 뒤 새 제출을 중단했고 이미 시작된 나머지 요청을 drain했다.

| concurrency | 실패 직전 시작 요청 | drain 성공 | 명시적 재개 시 실패 요청 재시도 | 성공 요청 재전송 |
|---|---:|---:|---:|---:|
| 1 | 1 | 0 | 1 | 0 |
| 2 | 2 | 1 | 1 | 0 |
| 3 | 3 | 2 | 1 | 0 |
| 4 | 4 | 3 | 1 | 0 |

24건 모두 재개 후 필수 작업 완료·부분 성공 반환 금지를 확인했다. 재개 호출 수는 N-(c-1)이다.
이 장애 시나리오의 cooldown도 Mock 비교에서 제외했다. 기본 운영은 공유 cooldown을 유지한다.

추가 단위 검증: 동시 영구/일시 오류에서 영구 오류 우선, 413/422/인용 불일치 무재시도,
계획 불일치·변조 checkpoint 거부, quota/TPM 추정 차단, 429 Retry-After, adaptive 동시성 축소,
두 문서 공유 admission, Ctrl+C/cancel drain, crash in-flight 불명확 상태 보호,
기존 checkpoint 복사 이관, 실제 SDK+HTTPX MockTransport 옵션 분리·숨은 HTTP 재시도 부재.

SDK는 설치된 google-genai 2.33.0의 동기 client로 검증했다. 실제 vendor 서비스 병렬 동작 검증은 아니다.
실제 계정 RPM/TPM/RPD·요금은 확인하지 않았다. 일일 한도는 병렬화나 간격 조정만으로 해결되지 않는다.

## 적용 범위와 미검증

- 새 run_bounded_bulk는 caller 실행기다. 기존 run_bulk/Java 제안 helper가 자동으로 병렬화되지 않는다.
- AI_EXTRACT_CONCURRENCY 기본1, 서버 gate 자체는 별도 동시성/timeout Mock 검증을 통과했다.
  실전 parallel2를 보려면 caller/server 양쪽을 테스트에서만2로 맞추고 worker1개로 시작해야 한다.
- 기존 API JSON·무손실 계획·인용 검증·후보 범위·explain 안정화/독립 검토는 유지한다.
- Docker·Java 병렬 helper·실제 Spring 상태 조회/프록시·실제 Gemini 병렬 성능은 미검증이다.
- 기존 5분 전체 block/무조건 전체 재시도와 장시간 polling/체크포인트 영속성·F-21 연동은 별도 과제다.

상세 수치와 private fault matrix는 Git 제외된 test_results/parallel_bulk_offline_summary.json에만 저장했다.
